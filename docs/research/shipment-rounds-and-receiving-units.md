# 입고 계층 조사: 계획 차수, 입고 단위, 물리 선적 (SAP, Dynamics, Oracle, NetSuite)

범례는 다음과 같습니다.

- **확인**: 벤더 문서나 법령 원문을 직접 읽음.
- **추정**: 검색 요약, 커뮤니티, 블로그 기반.
- **미확인**: 근거를 찾지 못함.

help.sap.com 신형 페이지는 JS 렌더링으로 열리지 않았고, SAP 커뮤니티는 403이었습니다. 그래서 SAP 쪽은 구형 saphelp 라이브러리, learning.sap.com, 테이블 사전에 의존했습니다. 기존 두 보고서의 EKET/EKES/LIKP/LIPS 필드 설명은 반복하지 않았고, 새로 확인한 부분만 적었습니다.

## 먼저 결론

- **SAP는 "어느 계획 차수에 이 ASN/입고가 속하는가"를 저장하지 않습니다.** 차수(EKET)는 계획 슬롯입니다. 입고와 ASN은 PO 라인에 붙고, 차수와는 사후에 날짜순으로 맞춰집니다. 그래서 "차수를 미리 만들지 않으면 ASN을 건너뛴다"는 제약은 SAP에는 없고, 이 도구의 설계에서 나온 제약으로 보입니다.
- **업계 표준은 "물리 선적"과 "입고 이벤트"를 분리하는 것입니다.** 한 선적(B/L)에 입고 기록이 여러 번 생기는 것은 선적을 쪼개서가 아니라 입고 이벤트를 여러 개 기록해서 처리합니다.
- **현재 도구의 "차수"는 세 역할을 한 객체가 맡고 있을 가능성이 큽니다.** 계획 슬롯, 입고 단위, 물리 선적의 일부가 합쳐진 상태입니다. 같은 송장번호를 손으로 적어 묶는 것은 빠진 세 번째 계층(물리 선적)을 사람이 흉내 내는 것으로 보입니다. 이는 추정이며, 아래 질문으로 확인해야 합니다.

### 계층 대응

| 개념                      | SAP 객체                               | 비고                                                                                                                        |
| ------------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 계획된 납품 차수          | EKET (PO 라인 아래)                    | 계획 슬롯. GR과 FK 관계 없음                                                                                                |
| 공급자 응답               | EKES (PO 라인 아래)                    | 주문확인(AB)과 출하통지(LA)를 확인 통제 키로 순서화. 라인 단위이고 차수 단위가 아님                                         |
| 입고 단위                 | LIKP/LIPS 인바운드 딜리버리            | 통지된 한 건의 납품이자 창고가 받는 문서. 라인이 PO 품목(VGBEL/VGPOS)을 참조. B/L 번호(BOLNR)와 차량(TRAID)은 헤더의 참조값 |
| 물리 선적(차량, 컨테이너) | VTTK/VTTP 운송문서, TM의 freight order | 여러 딜리버리를 묶음. 선택 모듈이라 없는 회사도 많음                                                                        |
| 포장 단위                 | HU(VEKP), SSCC                         | ASN에서 HU가 딜리버리에 생성되고 EWM이 이를 복사함(확인)                                                                    |

인바운드 딜리버리는 "통지된 납품"과 "창고 입고 문서"를 겸하는 객체입니다. 그래서 EWM의 딜리버리 분할은 **입고 문서만 쪼개고 물리 선적은 그대로**입니다. "트럭 한 대 대신 두 대"가 문서에 명시된 대표 사례입니다.

딜리버리 생성의 전제는 스케줄 라인이 아닙니다. 확인 통제 키와 PO 품목이 전제입니다. "Create Inb. Delivery"가 켜져 있으면 ASN 없이도 PO에서 딜리버리를 만들 수 있습니다(확인). PO 품목에 스케줄 라인이 최소 1개 있다는 점은 일반 지식으로 추정합니다.

### 보편적 합의

- 계획(스케줄/차수)과 실행(딜리버리/로드/입고)은 서로 다른 객체이고, 연결은 PO 라인에서 이뤄집니다.
- 입고 후 수량은 계획 슬롯에 사후 배분되거나 미결 수량 계산에만 쓰입니다.
- 입고 문서의 분할은 "아직 창고 활동이 없을 때"만 허용됩니다.

### 특수 상황과 대응

- 한 PO가 여러 창고로 가는 경우는 창고 번호별로 딜리버리가 자동 분리됩니다(추정).
- 입고 전 수량 조정과 분할은 되돌릴 수 없으므로 사유 코드(프로세스 코드)를 남깁니다.

### 보편적 합의

- **문서화된 분할 사유는 실제로 둘로 갈립니다.** 화물이 나뉘어 도착하는 경우와 신고가 나뉘는 경우입니다.
- 소유권 시점, 품질 보류, 입고 시점 차이는 대부분 **상태나 이벤트로 흡수**하며, 선적 객체를 쪼개는 이유로는 문서화되지 않았습니다.
- 한국 통관에서 B/L은 신고의 기본 단위이고, 분할은 사유가 있어야 하는 예외입니다. 분할 후에도 B/L 번호는 같고 화물관리번호가 추가됩니다. 이 점이 "같은 송장/운송장 번호를 적어 묶는" 현재 관행과 구조적으로 닮았습니다(추정).

### 특수 상황과 대응

- 통관이 나뉘면 입고도 나뉘기 쉬우므로, 통관 단위(신고번호, 화물관리번호)를 선적 아래 별도 속성으로 두는 모델이 Dynamics의 Folio와 같은 방향입니다.
- 사후에 "제조사가 나눠 보냈다"는 사실이 밝혀지는 경우는 EWM이 문서화한 정상 시나리오입니다. 단, 창고 활동 전이어야 하고 되돌릴 수 없습니다.

### 보편적 합의

- **매칭 키는 "PO + 라인"입니다. 계획 차수가 아닙니다.** PO 라인이 없으면 거부하거나 보류하고, PO 라인이 있으면 수신 단위를 자동 생성합니다.
- 수량 불일치는 대체로 경고, 허용 오차, 정정 요청으로 처리하며, 조용히 건너뛰는 시스템은 찾지 못했습니다.

### 특수 상황과 대응

- 초과 수량은 허용 오차 설정으로 통제합니다.
- 완전히 모르는 화물은 Oracle의 무발주 수령(미확인)이나 Dynamics의 도착 시 load 자동 생성으로 사후 정리합니다.

## 소유자 확인이 필요한 질문

1. 차수를 PO 안에 미리 만들어야 하는 이유는 무엇입니까? 납기 관리, 시리얼 배정, 지급 조건 연결, 화면 구조 중 어느 쪽입니까?

3. "입고가 따로"는 무엇이 다른 경우입니까? 창고, 도착일, 통관 건, 검수 결과 중 어느 쪽입니까?

7. 재무에서 차수 단위로 필요한 값(소유권 이전일, 결제 시점)이 있습니까?
