# 테스트 정책

무엇을 자동화하고 무엇을 사람(에이전트)이 직접 돌려 확인하는지에 대한 규칙이다.
변경을 검증하기 전에, 그리고 PR 의 `검증` 항목을 쓰기 전에 읽는다.

## 자동화하는 것 (`pnpm test`, CI)

| 층             | 대상                                                       | 위치·이름                                           | 조건                                  |
| -------------- | ---------------------------------------------------------- | --------------------------------------------------- | ------------------------------------- |
| 도메인 단위    | `domain/` 의 순수 함수 (상태 전이, 계산)                   | 파일 옆 `*.spec.ts` (예: `unit-projection.spec.ts`) | 반드시 작성                           |
| application    | `*Service` — repository 인터페이스의 메모리 구현으로       | 파일 옆 `*.spec.ts` (예: `order.service.spec.ts`)   | 규칙이 서비스에 걸쳐 있으면 작성      |
| 패키지 DB 통합 | `@repo/db-kit` 의 아웃박스·인박스가 실제 MySQL 에서 맞는지 | `packages/db-kit/src/outbox.integration.spec.ts`    | `TEST_DATABASE_URL` 이 있을 때만 실행 |

- 프레임워크는 Vitest 하나다. 다른 테스트 러너를 들이지 않는다.
- DB 통합 테스트는 `TEST_DATABASE_URL` 이 없으면 사유를 남기고 건너뛴다 (`pnpm check` 는 DB 없이도 초록이다).
  URL 의 데이터베이스 이름은 `_test` 로 끝나야 하고, 테스트가 만들고 지운다. CI 는 MySQL 서비스 컨테이너로 이 변수를 넣어 실제로 돌린다.

  ```sh
  TEST_DATABASE_URL=mysql://root:root@localhost:3306/lh_messaging_test mise exec -- pnpm test
  ```

- 새 DB 통합 테스트도 같은 방식(`TEST_DATABASE_URL`, 건너뛰기, `_test` 접미사, 스스로 만들고 지우기)을 따른다.

## 자동화하지 않는 것

**HTTP 수준 이상의 테스트(서비스 e2e, 서비스 간 흐름, 웹 콘솔)는 코드로 두지 않는다.** 소유자의 결정이다.
그 층은 **에이전트가 실제로 떠 있는 시스템을 플레이북대로 조작해서** 확인한다. 플레이북은 [playbooks/](playbooks/README.md) 에 있다.

- 단위 테스트 위의 모든 동작 검증은 플레이북 실행 결과로만 증명한다. `pnpm check` 통과는 "컴파일되고 순수 규칙이 맞다"는 뜻이지 "동작한다"는 뜻이 아니다.
- e2e 테스트 코드, supertest 류 HTTP 테스트, 데모 스크립트의 CI 실행을 추가하지 않는다. 필요하다고 판단되면 구현하지 말고 사용자에게 묻는다.

## 단위 테스트 위의 변경을 검증하는 방법

1. 인프라와 서비스를 띄운다 ([playbooks/README.md](playbooks/README.md) 의 "준비"). 서브에이전트는 자기 포트와 DB 를 쓴다 (`docs/agent-workflow.md`).
2. 바뀐 동작에 해당하는 플레이북(들)을 **처음부터 끝까지** 한 단계씩 실행한다. 바뀐 부분만 골라 돌리지 않는다 — 앞 단계가 뒤 단계의 데이터를 만든다.
   - 서비스 코드를 바꿨으면 그 서비스의 플레이북. 이벤트를 내거나 받는 코드를 바꿨으면 `cross-service.md` 까지.
   - 웹 콘솔을 바꿨으면 `web-console.md`. 브라우저 조작은 Claude in Chrome 으로 한다.
3. PR 의 `검증` 항목에 **실제로 본 것**을 적는다: 실행한 플레이북과 단계 번호, 관찰한 상태 코드·본문·화면 내용. 기대와 다른 것이 있으면 그대로 적고 `미검증` 이나 본문에 사유를 쓴다.
   - 플레이북을 돌리지 않았으면 "돌리지 않았다"고 쓴다. 돌리지 않은 플레이북을 통과했다고 쓰지 않는다.
   - 검토자는 `검증` 에 플레이북 파일과 단계 번호, 관찰 결과가 있는지 본다 (`docs/agent-workflow.md` 의 "검토 기준").

## 기능을 추가하거나 버그를 고칠 때

- **기능 추가**: `docs/architecture-rules.md` 의 "기능을 추가하는 순서"대로 만들면서, 1단계(domain)의 순수 함수에는 단위 테스트를, 끝 단계(presentation)에는 **같은 PR 에서 플레이북 단계를 추가하거나 고친다.** 기대값은 추측하지 말고 실제 응답을 붙여 넣는다.
- **버그 수정**: 원인이 순수 규칙(domain, application)에 있으면 **먼저 실패하는 단위 테스트를 쓰고** 고쳐서 통과시킨다. 그 밖(쿼리, 트랜잭션, 이벤트, HTTP)이면 버그를 재현하는 플레이북 단계를 추가하고, 고친 뒤 그 단계의 기대값을 바로잡는다.
- 플레이북의 기대값이 현재 동작과 다르다는 것을 발견하면 코드를 고치지 말고 PR 의 `미검증` 에 적어 메인 에이전트가 판단하게 한다.

## 테스트 모드 (예약, 미구현)

지금은 외부 연동(업체 WMS, 택배사, 판매 채널)이 없어 서비스가 모두 자기 DB 와 메시지 버스만 본다.
연동 어댑터가 생기면 플레이북을 돌릴 때 실제 업체 시스템을 부르지 않도록 **어댑터를 목으로 바꾸는 모드**가 필요하다.
그 설정 이름은 `APP_MODE=test` 로 예약한다 (`@repo/nest-kit/config` 의 네임스페이스로 읽는다). 지금은 구현하지 않고, 첫 외부 연동을 추가하는 PR 에서 같이 만든다.
