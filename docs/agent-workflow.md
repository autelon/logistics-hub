# 에이전트 작업 방식

이 리포의 코드 작업은 **메인 에이전트가 나누고, 서브에이전트가 만들고, `reviewer` role 이 검토해 병합한다.** 모든 PR 은 `autelon:security-reviewer` 의 보안 검토도 받는다.
사용자는 방향을 정하고 결과를 본다. 사람이 PR 을 하나씩 승인하지 않는다.

## 역할

**메인 에이전트**

- 요청을 서로 독립적으로 병합할 수 있는 작업 단위로 나눈다. 같은 파일을 고치는 작업은 한 단위로 묶거나 순서를 정한다.
- 작업마다 서브에이전트(`developer` role)를 격리된 worktree 에서 실행한다. 독립적인 작업은 동시에 실행한다.
- 코드를 직접 고치지 않는다. 예외는 규칙·맥락 문서(`CLAUDE.md`, `docs/`)와 한두 줄짜리 수정이다.
- PR 이 올라오면 `reviewer` role 에 검토를, `autelon:security-reviewer` 에 보안 검토를 맡긴다. 수정 요청이 오면 같은 서브에이전트에게 지시한다.

**서브에이전트**

- 맡은 작업 하나만 한다. 범위 밖의 문제를 발견하면 고치지 말고 PR 본문의 `미검증` 에 적는다.
- 시작할 때 `CLAUDE.md`, `docs/git-rules.md`, `docs/architecture-rules.md` 를 읽는다.
- `origin/main` 에서 브랜치를 만들고, 규칙에 맞는 커밋을 쌓고, `pnpm check` 가 통과한 뒤 PR 을 올린다.
  단위 테스트 위의 동작(HTTP, DB, 이벤트, 웹 콘솔)을 건드렸으면 `docs/testing.md` 대로 해당 플레이북(`docs/playbooks/`)을 실제로 돌리고, 실행한 단계와 관찰한 결과를 PR 의 `검증` 에 적는다.
- PR 을 올리면 PR 번호와 함께 무엇을 검증했고 무엇을 못 했는지 보고하고 끝낸다. 스스로 병합하지 않는다.
- 검증용으로 띄운 프로세스는 **자기 PID 만** 멈춘다 (`lsof -ti:<포트>`). `pkill -f 'node dist/main.js'` 같은 광범위한 종료는 동시에 작업 중인 다른 에이전트의 프로세스를 죽인다 (실제로 일어났다).
- 공유 자원을 쓰지 않는다. 포트 3001–3004 와 DB `lh_scm`·`lh_oms`·`lh_as` 는 메인 에이전트가 전체 데모에 쓴다. 서브에이전트는 자기 포트와 자기 DB(`lh_<앱>_<작업>`)를 만들어 쓰고 끝나면 지운다. Redis 컨슈머 그룹은 공유되므로 서비스 간 흐름 검증은 메인 에이전트가 한다.

## 서브에이전트에게 줄 지시

서브에이전트는 이 대화를 모른다. 지시에는 다음이 들어가야 한다.

- 목표와 완료 조건. 무엇이 되면 끝인지.
- 범위. 고쳐도 되는 워크스페이스·폴더와, 건드리면 안 되는 것.
- 이미 정해진 결정. 다시 고민하지 않게.
- 읽어야 할 문서와 파일 경로.
- 동시에 진행 중인 다른 작업과 겹칠 수 있는 지점.

## 검토 기준

검토자(`reviewer` role)는 PR 본문의 설명을 믿지 않고 diff 와 CI 를 직접 본다.

병합한다:

- CI `check` 통과.
- 변경이 맡긴 범위 안에 있다.
- `docs/architecture-rules.md` 의 레이어·의존 규칙과 `CLAUDE.md` 의 설계 원칙을 지킨다.
- 커밋 메시지가 `docs/git-rules.md` 를 따르고, `검증`·`미검증` 이 실제와 맞다.
- 동작이 바뀌었으면 확인한 근거가 있다: 순수 규칙은 단위 테스트, 그 위는 PR 의 `검증` 에 **실제로 돌린 플레이북 파일·단계 번호와 관찰한 상태 코드·본문·화면 내용**이 적혀 있다 (`docs/testing.md`).
  "플레이북 통과"라고만 적혀 있고 관찰 결과가 없으면 돌리지 않은 것으로 본다. presentation 을 바꿨는데 플레이북 수정이 없으면 돌려보낸다.
- 같은 head sha 에 `autelon:security-reviewer` 의 `보안 검토: 통과 (<sha>)` 코멘트가 있다 (`docs/git-rules.md` "PR 리뷰어와 보안 검토").

돌려보낸다 (PR 에 사유를 댓글로 남기고 같은 서브에이전트에게 수정을 지시):

- 규칙 위반, 범위 이탈, 검증 없이 "동작한다"고 적은 경우.
- 린트·타입 검사를 끄거나 우회한 경우.
- 설계 결정이 필요한 문제를 임의로 정한 경우. 이때는 사용자에게 묻는다.

병합은 검토한 `reviewer` role 이, 같은 head sha 에 리뷰 통과 코멘트와 `보안 검토: 통과 (<sha>)` 코멘트가 둘 다 있을 때만 머지 큐에 넣는 것으로 한다: `gh pr merge <PR> --match-head-commit <검토한 head sha>`.
검사가 아직 돌고 있으면 auto-merge 가 켜지고, 통과했으면 큐에 들어간다. 검토 뒤 브랜치가 바뀌었으면 sha 가 달라 병합되지 않는다. `--admin` 은 쓰지 않는다.
서브에이전트는 병합·auto-merge 명령을 쓰지 않는다. 사용자가 "이 PR 은 내가 리뷰한다"고 한 PR 은 메인 에이전트와 `reviewer` role 도 병합 명령을 내지 않는다.
큐에서 충돌로 빠지면 그 PR 의 서브에이전트에게 rebase 후 `--force-with-lease` 로 다시 올리게 한다(`docs/git-rules.md`).
원격 브랜치는 직접 지우지 않는다. 저장소 설정(병합 시 브랜치 자동 삭제)이 지운다. 병합 전에 손으로 지우면 PR 이 닫힌다 (실제로 일어났다).
같은 계정으로 올린 PR 이라 GitHub 의 승인(approve) 기능은 쓸 수 없다. 검토 결과는 댓글로 남긴다.

## 근거 없이 결정하지 않는다

메인 에이전트와 서브에이전트 모두에게 적용된다.

- 추정을 근거로 결정하거나 구현하지 않는다. 확인한 사실(실행 결과, 읽은 코드·문서, 출처가 있는 자료)에 근거한다.
- 확인하지 않은 것을 확신하는 말투로 쓰지 않는다. PR 본문과 보고에서 확인한 것, 추정한 것, 모르는 것을 구분한다.
- 조사해도 알 수 없으면 정하지 말고 메인 에이전트에게(메인 에이전트는 사용자에게) 넘긴다: 무엇을 정해야 하는지, 확인한 사실과 출처, 추정과 그 이유, 선택지.
- **물류 실무에 관한 결정은 특히 그렇다.** 일반 관행은 원출처로 조사한다. 우리 거래처·계약의 실제 사정을 알아야 정할 수 있는 것은 사용자에게 조사를 요청한다. 누구에게 무엇을 물으면 되는지 구체적으로 적는다.
  설계 문서에 "가정"으로 적어 두고 진행하지 않는다.
- 되돌리기 쉬운 구현 세부(이름, 파일 위치)는 대상이 아니다.

## 사용자에게 묻는 경우

- 요구가 둘 이상으로 해석되고 결과가 크게 달라질 때.
- 설계 원칙이나 규칙 문서를 바꿔야 할 때.
- 되돌리기 어려운 일(데이터 삭제, 외부 공개, 비용 발생)일 때.
