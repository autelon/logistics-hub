# 6. 구매·입고 설계안

> **상태: 확정된 설계. 아직 구현되지 않았다.** 사용자 확인(2026-10-03)이 반영됐다. "결정 전에 확인이 필요한 것"에 남은 항목은 구현을 막지 않으며, 해당 필드를 선택 항목으로 두고 답이 오면 채운다. 구현이 끝나면 이 문서의 내용을 [02-domain-model.md](02-domain-model.md) 로 옮기고 이 파일은 지운다.
> [02-domain-model.md](02-domain-model.md) 로 옮기고 이 파일은 지운다.

발주서를 기준으로 선적이 여러 건 등록되고, 그 선적이 외부 창고에 입하·입고·적치되는 흐름을 기록한다.
지금의 제품(시리얼) 이력 위에 **문서 단위의 층**을 올리는 일이다.

## 범위

| 한다                                                           | 하지 않는다                                    |
| -------------------------------------------------------------- | ---------------------------------------------- |
| 발주 등록·변경·종결                                            | 발주 승인 결재, 제조사와의 가격 협상           |
| 제조사·포워더가 알려 주는 선적, 운송 서류, 운송 진행 상황 기록 | 운송 예약·배차                                 |
| 창고가 보고하는 입하·검수·입고·적치 기록                       | 창고 내 작업 지시                              |
| 발주 → 선적 → 입고의 단계별 수량 차이와 이상 표시              | 재고 평가(이동평균, 부대비용 배부), 환율, 세금 |
| 시리얼·로트·수량 세 가지 추적 방식                             | 포장 계층(팔레트·카톤, SSCC) — 필요해지면 추가 |

발주는 OMS 가 아니라 `scm-api` 에 둔다. OMS 는 우리가 **받는** 판매 주문이고, 발주는 우리가 **내는** 구매 주문이다.

## 원칙의 적용

[01-concept.md](01-concept.md) 의 세 원칙이 문서 층에도 그대로 적용된다.

- **발주는 우리가 만든 문서다.** 고칠 수 있지만, 발행한 뒤의 변경은 이력을 남긴다.
- **선적·운송·입고는 업체가 보고한 사실이다.** 추가만 하고, 틀렸으면 정정 기록으로 무효화하거나 대체한다. SAP 가 자재 문서를 고치지 않고 역분개 문서로 취소하는 것과 같은 방식이다.
- **모순은 거부하지 않고 이상으로 표시한다.** 발주 수량을 넘는 선적, 선적 통지 없이 도착한 입고, 통지에 없던 시리얼 등.
- **우리가 내리는 명령은 검증하고 거절할 수 있다.** "거부하지 않는다"는 업체가 보고한 사실에만 적용된다. 발주 발행, 제품 등록처럼 우리가 내리는 명령은 전제 조건을 검사하고 맞지 않으면 거절한다(에러 코드).
- **두 개의 시간.** 모든 사실에 일어난 시각과 기록한 시각을 따로 둔다. 해운 표준(DCSA Track & Trace)도 같은 구분을 쓴다.

## 도메인 모듈

`apps/scm-api/src/domains/` 에 추가한다. 이름은 **사실을 보고하는 외부 시스템과 1:1** 로 맞춘다. 사용자가 그린 전체 구조
(주문 → WMS → TMS, 발주 → inbound TMS → WMS, AS → TMS → WMS → TMS)에서 WMS 와 TMS 가 그대로 도메인 이름이 된다.

| 도메인           | 보고 주체                         | 내용                                                                                                     |
| ---------------- | --------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `procurement`    | 우리(구매 담당)                   | 발주서와 발주 줄, 개정, 종결                                                                             |
| `transport`      | 제조사·포워더·운송사·택배사 (TMS) | 선적, 선적 줄, 운송 서류, 컨테이너, 운송 진행 사실. 정흐름 입고·출고 배송과 역흐름 회수 운송이 모두 여기 |
| `warehouse`      | 3PL 창고 (WMS)                    | 입하·검수·입고·적치 보고, 시리얼 없는 제품의 수량 원장, 재고 조회                                        |
| `catalog` (기존) | 우리                              | 제품(추적 방식 추가)·거점                                                                                |
| `unit` (기존)    | — (다른 도메인이 쓴다)            | 제품 한 개의 이력. 세 흐름이 만나는 지점이라 `transport` 와 `warehouse` 의 사실이 여기에 참조를 남긴다   |

- 지금 `unit` 에 있는 `SHIPPED`·`DELIVERED`·`RETURN_RECEIVED` 사실은 그대로 둔다. 창고와 운송사가 보고하는 개체 단위 사실이고, 문서 층(`transport` 의 선적, `warehouse` 의 입고 보고)이 그 위에 참조를 더하는 구조다.
- 앞 절의 "stock" 은 별도 도메인이 아니라 `warehouse` 안의 수량 원장이다.
- 역흐름(회수 운송 → 창고/서비스센터 → 공장 반송·재입고·폐기)은 별도 조사 뒤 이 문서에 절을 추가한다. 운송 구간은 `transport`, 창고 처리는 `warehouse`, 판정은 `as-api` 가 맡는 방향이다.

"발주 줄 하나의 단계별 수량"처럼 여러 도메인을 엮는 조회는 usecase 가 한다.

## 추적 방식

제품 기준 정보에 `tracking_mode` 를 둔다. SAP(배치 관리 플래그 + 시리얼 프로파일), Odoo(No tracking / By lots / By unique serial number) 모두 제품 단위로 정한다.

| 값       | 뜻                                                        | 재고의 근거              |
| -------- | --------------------------------------------------------- | ------------------------ |
| `SERIAL` | 개체마다 고유 번호. 제조사가 생산 즉시 우리 규칙대로 부여 | 제품 이력(`unit_events`) |
| `LOT`    | 같은 조건으로 만든 묶음에 번호 하나                       | 수량 원장, 로트별        |
| `NONE`   | 수량만                                                    | 수량 원장                |

- `SERIAL` 제품에는 `serial_pattern`(정규식)을 둘 수 있다. 보고된 시리얼이 규칙과 다르면 받아들이고 이상으로 표시한다.
- 로트 번호 칸은 선적 줄·입고 줄·수량 원장에 처음부터 둔다(nullable). 지금 로트 제품이 없어도 나중에 구조를 바꾸지 않기 위해서다.

## 선적 (`transport`)

발주 하나에 선적이 여러 건, 선적 하나에 여러 발주가 섞일 수 있다. **선적 헤더에는 발주 참조를 두지 않고, 선적 줄이 발주 줄을 가리킨다.** SAP 인바운드 딜리버리와 EDI 선적 통지(X12 856)가 같은 방식으로 다대다를 푼다.

**shipments** — 제조사·포워더가 알려 준 한 번의 출하

| 컬럼                                        | 필수 | 설명                                |
| ------------------------------------------- | ---- | ----------------------------------- |
| `shipment_no`                               | ✓    | 우리 내부 번호                      |
| `shipper`, `mode`, `destination_location`   | ✓    | `mode`: `SEA` / `AIR` / `ROAD`      |
| `international`                             | ✓    | 국내·국제                           |
| `source_system`, `reported_at`              | ✓    | 누가 언제 알려 줬나                 |
| `supplier_delivery_note_no`                 |      | 제조사 납품서·패킹리스트 번호       |
| `forwarder`, `origin`, `ship_date`, `eta`   |      |                                     |
| `import_declaration_no`, `cargo_control_no` |      | 수입신고번호, 화물관리번호 (국제만) |

**shipment_lines**

| 컬럼                                        | 필수 | 설명                      |
| ------------------------------------------- | ---- | ------------------------- |
| `purchase_order_line_id`                    | ✓    | 다대다를 푸는 지점        |
| `sku`, `shipped_qty`                        | ✓    |                           |
| `lot_no`, `manufacture_date`, `expiry_date` |      | 로트가 다르면 줄을 나눈다 |
| `container_id`                              |      |                           |

`shipment_line_serials(shipment_line_id, serial_number)` — `SERIAL` 제품의 시리얼 목록. 입고 검수 때 대조 기준이 된다.

**transport_documents** — B/L 만을 위한 구조를 만들지 않고 운송 서류 하나로 일반화한다.

| 컬럼                                                  | 필수 | 설명                                                                     |
| ----------------------------------------------------- | ---- | ------------------------------------------------------------------------ |
| `type`                                                | ✓    | `MBL` / `HBL` (해상), `MAWB` / `HAWB` (항공), `ROAD_WAYBILL` (국내 육상) |
| `document_no`                                         | ✓    |                                                                          |
| `parent_document_id`                                  |      | House → Master                                                           |
| `issuer`, `issue_date`, `booking_no`                  |      |                                                                          |
| `vessel_name`, `voyage_no`, `flight_no`, `vehicle_no` |      | 수단에 따라                                                              |
| `port_of_loading`, `port_of_discharge`                |      | 항구는 UN/LOCODE, 공항은 IATA 코드                                       |

- 선적과 운송 서류는 조인 테이블로 잇는다. B/L 하나가 여러 선적을 덮을 수 있다.
- `containers(container_no, seal_no, size_type, load_type)` 와 운송 서류도 다대다다. B/L 하나에 컨테이너 여러 대(FCL), 컨테이너 하나에 House B/L 여러 장(LCL)이 실무에 모두 있다. 항공·육상에는 컨테이너가 없다.

## 입고 (`warehouse`)

### 입하와 입고를 나눈다

| 단계                 | 뜻                            | 재고 반영       | 기록하는 수량                                    |
| -------------------- | ----------------------------- | --------------- | ------------------------------------------------ |
| 입하 `ARRIVAL`       | 차량·컨테이너 도착, 하차      | 아님            | 도착 수량(박스·팔레트 단위일 수 있음), 외관 파손 |
| 검수 `INSPECTION`    | 수량·상태 확인                | 아님            | 정상, 불량·파손, 회송                            |
| 입고 `GOODS_RECEIPT` | 검수를 통과한 수량을 받아들임 | **여기서 반영** | 입고 확정 수량, 재고 상태                        |
| 적치 `PUTAWAY`       | 보관 위치에 놓음              | 위치만 확정     | 위치별 수량                                      |

- 나누는 근거: SAP 는 "도착했지만 미수락"(이동 유형 103)과 "수락"(105)을 별개로 전기하고, 창고 관리 모듈은 하차 → 입고 전기 → 적치를 따로 확인한다. EDI 입고 통지(X12 861, EDIFACT RECADV)는 수령·수락·차이 수량과 사유를 나눠 싣는다.
- **그러나 업체가 모든 단계를 보고하지는 않는다.** 조사에서 원문을 확인한 국내 풀필먼트 WMS 한 곳은 입하와 입고를 구분하지 않고 "입고" 한 번만 보고한다. 국내 3PL 이 일반적으로 어떻게 하는지는 확인하지 못했다.
- 그래서 **단계마다 사실 행을 따로 두고, `GOODS_RECEIPT` 만 필수**로 한다. 나머지는 업체가 주면 받는다.

**receipts** — 창고의 보고 한 건

| 컬럼                                          | 필수 | 설명                                                   |
| --------------------------------------------- | ---- | ------------------------------------------------------ |
| `stage`                                       | ✓    | `ARRIVAL` / `INSPECTION` / `GOODS_RECEIPT` / `PUTAWAY` |
| `location`                                    | ✓    | 창고                                                   |
| `occurred_at`, `recorded_at`, `source_system` | ✓    |                                                        |
| `shipment_id`                                 |      | 선적 통지 없이 도착하면 비어 있고, 이상으로 표시       |
| `warehouse_receipt_no`                        |      | 창고 쪽 입고 번호                                      |

**receipt_lines**

| 컬럼                                         | 필수 | 설명                                                   |
| -------------------------------------------- | ---- | ------------------------------------------------------ |
| `sku`, `quantity`                            | ✓    | 그 단계의 수량 (입하면 도착 수량, 입고면 확정 수량)    |
| `shipment_line_id`, `purchase_order_line_id` |      |                                                        |
| `rejected_qty`, `damaged_qty`                |      | 검수 단계                                              |
| `discrepancy_reason`                         |      | `SHORT` `OVER` `DAMAGED` `WRONG_ITEM` …                |
| `stock_status`                               |      | `AVAILABLE` / `HOLD` / `QC`                            |
| `lot_no`, `expiry_date`, `bin`               |      | `bin` 은 적치 단계. 창고가 위치를 공유하지 않으면 없다 |

`receipt_line_serials(receipt_line_id, serial_number)` — 실제로 받은 시리얼. 선적 통지의 목록과 대조한다.

부족·초과는 저장하지 않는다. 통지 수량과 받은 수량의 차로 계산한다.

**검사와 보관이 다른 곳일 수 있다.** 지금은 한 창고가 검사와 적치를 하지만, 업계에서는 입고 검사 장소와 보관 창고를 나누기도 한다. 입고 보고는 단계마다 `location` 과 보고 주체를 따로 가지므로 한 입고 흐름이 두 장소에 걸쳐도 그대로 담긴다. 능력 프로필도 장소·파트너마다 두므로 검사 장소에서만 `reports_inspection_result` 가 의미를 가진다.

### 재고에 반영되는 방식

`GOODS_RECEIPT` 가 기록되면 같은 트랜잭션에서:

- `SERIAL` 제품: 시리얼마다 제품 이력에 `RECEIVED` 사실을 추가하고 발주 줄·선적 줄 참조를 붙인다. 제품 한 개에서 "어느 발주의 어느 선적, 어느 B/L 로 들어왔나"를 거슬러 올라갈 수 있게 된다. `PUTAWAY` 는 `STORED` 사실이 된다.
- `LOT` / `NONE` 제품: 수량 원장에 이동을 추가한다.

정정도 같이 전파된다. 입고 보고를 무효화하면 그로 인해 생긴 제품 사실·수량 이동도 무효화·역분개된다.

## 소유권과 운송 중 재고

인도 조건(Incoterms)은 **위험이 넘어가는 시점**을 정할 뿐 소유권 이전을 정하지 않는다(ICC 가 명시). 소유권은 매매 계약에 따른다.
그래서 인도 조건에서 소유권을 자동으로 확정하지 않고, **데이터로 둔다.**

- 발주에 `ownership_transfer_point` 를 둔다: `ON_SHIPMENT`(출하 시) / `ON_BOARD`(본선 적재 시) / `ON_ARRIVAL`(도착 시) / `ON_RECEIPT`(입고 시).
- 인도 조건을 넣으면 기본값을 제안한다(FOB·CIF 계열은 `ON_BOARD`, DAP·DDP 계열은 `ON_ARRIVAL` 등). 사용자가 바꿀 수 있다.
- **운송 중인 우리 재고**는 따로 저장하지 않고 계산한다: 소유권 이전 지점에 해당하는 운송 사실이 `ACTUAL` 로 기록됐고 아직 입고 확정되지 않은 선적 줄의 수량.
- 재고 조회에 "창고 재고 / 운송 중(우리 소유) / 운송 중(아직 제조사 소유)" 구분이 생긴다.

지금처럼 운송 중에도 전부 우리 자산이면 발주마다 `ON_SHIPMENT` 를 쓰면 되고, 조건이 바뀌어도 구조는 그대로다.

## 발주 줄 하나로 보는 흐름

```
발주 100 ── 선적 60 ── 입하 60 ── 검수: 정상 58, 파손 2 ── 입고 58 ── 적치 58
         └─ 선적 40 ── (운송 중, 우리 소유)
```

usecase 하나가 발주 줄마다 `ordered / shipped / arrived / accepted / putaway` 와 각 단계의 차이를 계산해 준다. 수량은 어디에도 누계로 저장하지 않고 유효한 사실에서 매번 계산한다. 정정이 들어와도 어긋나지 않게 하기 위해서다.

## 이상으로 표시하는 것

- 선적 누계가 발주 수량 + 과납 허용을 넘음
- 닫힌 발주 줄, 없는 발주 줄에 대한 선적
- 선적 통지 없는 입고
- 입고 확정 수량이 선적 수량과 다름 (부족·초과)
- 선적 통지에 없던 시리얼이 입고됨, 통지된 시리얼이 입고되지 않음
- 시리얼이 제품의 `serial_pattern` 과 다름
- 컨테이너 번호 체크디지트 불일치
- 운송 사실의 순서가 맞지 않음 (출발 전에 도착 등)

## 역흐름 (반품·DOA 회수)

사용자가 그린 역흐름 AS → TMS → WMS → TMS 의 "그다음"을 조사했다
([research/reverse-logistics-routing.md](research/reverse-logistics-routing.md)). 업계 표준 단계는
승인 → 회수 → 입고·검사 → 처분 판정 → 이동이고(SCOR Return), 처분은 재입고·리퍼·수리·제조사 반송·매각·기부·재활용·폐기로 수렴한다.

### 공통 요소

- **반품 케이스** 하나가 경로 전체를 대표한다. 키: 반품 케이스 id, 반품 승인 번호(RMA), 원주문·원출고 참조, 시리얼, 사유 코드, 반품송장 번호(접수 직후엔 없을 수 있다).
- **계획 경로와 실제 경로를 따로 둔다.** SAP·Dynamics·Oracle 모두 RMA 시점에 계획을, 검사 후에 확정을 정한다. "불량 신고인데 정상"은 입고 후에야 드러나므로 둘이 다른 것은 이상이 아니다.
- **처분 판정과 처분 실행은 다른 사실이다** (SCOR 의 Disposition 과 Transfer). 판정만 있고 실행이 없으면 미완료로 추적한다.
- 사실마다 **보고 주체**와 **직접 보고/추론** 구분을 둔다. 검수 결과를 주지 않는 창고는 재고 존 이동·폐기 수량으로 추론할 수밖에 없다.

### 경로별 사실

| 경로           | 사실 순서 (보고 주체)                                                                                                                                                                                                    | 우리 재고 영향                                           |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| A. 창고 반품   | 반품 접수(채널·CS) → 반품송장 발번(3PL·채널) → 회수 집하·운송(택배사) → 창고 반품 입고(WMS) → 검수(WMS, 없을 수 있음) → 처분 판정(계약에 따른 판정자) → 처분 실행: 재입고 / 폐기 반출 / 반송 출고 / 서비스센터 이송(WMS) | 반품 입고로 들어왔다가 실행으로 나감                     |
| B. 서비스센터  | AS 접수(as-api) → 센터 도착(택배사·센터) → DOA 판정·판정서(센터) → 수리 후 반송 / 교체 / 센터 폐기 / 리퍼(센터)                                                                                                          | 교체품 출고 때만. 현품은 우리 창고를 거치지 않을 수 있다 |
| C. 제조사 반송 | 반송 승인·제조사 RMA(구매 담당·제조사) → 반송 출고(WMS) → 발송·인도(택배사) → 제조사 수령·검사(제조사, 보고 약함) → 크레딧·교체품 수령(구매·재무)                                                                        | 반송 출고로 차감                                         |

변형으로 고객 → 제조사 직송(SAP 후속 활동 0007)이 있다. 이 경우 우리 창고 사실은 없다.

### 도메인 배치

- 회수·반송 운송 구간은 `transport`, 반품 입고·검수·처분 실행은 `warehouse`, 제품 한 개의 반품·폐기·반송 사실은 `unit`.
- 반품 케이스와 처분 판정을 어디에 둘지는 아래 E 의 답에 달려 있다. as-api 는 지금처럼 DOA 판정만 맡는 방향이다.

## 제품 등록 (활성화)

적치까지 끝난 시리얼은 **이 시스템에서 제품으로 등록해야** 판매 가능한 개체가 된다. 등록된 개체는 기기 서버(기기 활성화 등을 처리하는 별도 API 서버)로 넘어가 기기 데이터가 만들어진다.
주문과 연결되어 출고될 수 있는 것은 등록된 개체뿐이다 (사용자 확인 2026-10-03).

### 등록 명령

- **운영자가 선적 단위로 "제품 등록하기"를 실행한다.** 자동이 아닌 이유는 업체가 잘못 기입한 것을 사람이 한 번 확인하기 위해서다.
- 등록은 **우리가 내리는 명령**이라 전제 조건을 검사한다. 명령은 선적 id(또는 그 안의 시리얼 일부)를 받아, 조건을 만족하는 개체만 등록하고 **제외한 시리얼과 사유**를 돌려준다.
  - 등록 가능: 제품이 `tracking_mode = SERIAL`, 개체가 `unit_receipt_trigger` 단계(지금은 적치) 이후로 확인됨, 아직 등록되지 않음.
  - 제외 사유 예: 입고 미확인(부족 입고라 개체 단위로 추론하지 않은 경우), 이미 등록됨, 시리얼 관리 제품이 아님. **부족 입고 선적은 운영자가 정정하거나 확인하기 전까지 해당 개체를 등록할 수 없다.** 사람이 확인하는 이유가 바로 이 경우다.
  - 이미 등록된 시리얼을 다시 등록하면 기존 결과를 돌려준다(멱등).
- 등록되면 제품 이력에 `REGISTERED` 사실(출처 `logistics-hub`, 처리자 = 운영자)을 남긴다.
- 등록은 물리 상태와 다른 축이다. 상태 전이 표(`RULES`)는 물리 사실만 다루고, `REGISTERED` 는 개체 상태의 `registeredAt` 만 채운다. 그 사실이 무효화되면 비운다.
- 자동 등록은 정책 값 `auto_register_on_putaway`(기본 거짓)로 둔다. 참이면 적치 사실이 들어올 때 같은 등록 usecase 를 부른다. 별도 구현이 거의 없어서 둔다.

### 미등록 출고는 이상 표시만 한다 (규칙)

등록되지 않은 시리얼 개체가 출고·배송되면 받아들이고 이상으로 표시한다. **자동으로 등록하지 않는다.**
실제로 시스템이 꼬여 먼저 출고하고 나중에 DB 를 고친 일이 있었고, 출고된 것이 알고 보니 다른 시리얼인 경우도 있다. 상황마다 대처가 달라 사람이 판단해야 한다.

### 기기 서버와의 연동: 변경 피드 (권장안)

기기 서버는 API 서버이고 연동 방식은 우리가 정한다. 보내야 하는 것은 두 가지다: **활성화**(등록됨)와 **비활성화**(DOA·폐기되거나 등록이 정정됨).

| 방식                    | 내용                                                                                        | 장점                                                                                                                                                        | 단점                                                                                            |
| ----------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| A. 대량 푸시            | 등록할 때 시리얼 목록을 담아 기기 서버 API 를 호출                                          | 가장 단순                                                                                                                                                   | 큰 선적은 나눠 보내야 하고, 우리 쪽에 재시도 작업자가 필요하다. 비활성화는 별도 경로가 필요하다 |
| B. 알림 후 당김         | 등록 요청 id 만 보내고, 기기 서버가 그 id 의 시리얼 목록을 가져감                           | 보내는 내용이 작고 기기 서버가 속도를 정함                                                                                                                  | 등록만 다룬다. 비활성화를 담으려면 또 다른 경로가 필요하다                                      |
| **C. 변경 피드 (권장)** | 우리가 "개체별 활성 여부가 바뀐 기록"을 순서대로 쌓고, 기기 서버가 커서로 주기적으로 가져감 | 활성화·비활성화가 한 줄의 순서 있는 흐름이 된다. 커서가 있어 재시도 작업자 없이 최소 한 번 전달이 되고 중복에 강하다. 기기 서버가 자기 속도로 배치 처리한다 | 지연이 폴링 주기만큼 생긴다. 기기 서버가 폴링과 커서 저장을 구현해야 한다                       |

C 를 권하는 이유는 사용자가 이미 업체 연동을 배치로 당겨 오는 방식을 쓰고 있고(실시간성이 급하지 않고 묶어 처리하는 편이 효율적), 비활성화도 같은 통로로 보내야 하기 때문이다. B 는 C 를 등록에만 한정한 것이다.

**피드의 동작**

- 개체마다 "기기 서버에서 활성이어야 하는가"를 상태에서 계산한다: `registeredAt` 이 있고 상태가 `DOA`·`SCRAPPED` 가 아니면 활성.
- 사실이 기록되거나 정정되어 개체를 다시 접을 때, 이 값이 바뀌면 피드에 한 줄을 쌓는다(같은 트랜잭션). 등록 → `ACTIVATE`, DOA·폐기 → `DEACTIVATE`, 등록 정정 → `DEACTIVATE`, DOA 사실이 정정되어 되돌아가면 → `ACTIVATE`. 값이 그대로면 쌓지 않는다.
- 한 줄: 순번, 시리얼, SKU, 동작(`ACTIVATE` / `DEACTIVATE`), 사유, 등록 요청 id(있으면), 기록 시각.
- 기기 서버: `GET /device-sync/changes?after=<커서>&limit=<N>` 으로 가져가 처리하고 커서를 저장한다.
- 처리 결과: 기기 서버가 `POST /device-sync/results` 로 시리얼별 성공·실패를 알려 주면 운영자 화면에 "활성화됨 / 실패"를 보여 준다.
- 모노레포에 **모의 기기 서버**(`apps/device-api`)를 둔다. 피드를 주기적으로 가져가 로그를 남기고 결과를 돌려주는 최소 구현이며, 등록 플레이북을 끝까지 실행할 수 있게 하는 것이 목적이다.

## 업체 연동 방식: 배치로 당겨 온다

TMS·WMS 현황은 업체가 건마다 보내 주는 것이 아니라 **우리가 배치로 한꺼번에 불러와 확인한다** (사용자 확인 2026-10-03).
실시간성이 급하지 않고, 업체 시스템 구조의 제약도 있으며, 묶어서 처리하는 편이 효율적이기 때문이다(DB 쿼리를 모아 최적화하는 등).
지금까지의 설계는 업체가 정규화된 사실을 우리 API 로 보낸다고 가정했으므로, 연동 계층을 이렇게 바로잡는다.

- 업체별 어댑터는 `presentation/batch/` 에 둔다(레이어 규칙에 이미 있는 자리). 주기적으로 업체 API·파일을 불러와 정규화하고 usecase 를 부른다.
- 어댑터마다 **체크포인트(커서)** 를 둔다. 어디까지 가져왔는지 기록해 다음 배치가 이어서 가져간다.
- 멱등 키는 업체 쪽 레코드 id 로 만든다. 같은 레코드를 다시 가져와도 한 번만 기록된다.
- **대량 기록 usecase** 를 둔다. 배치 하나의 사실을 한 트랜잭션(또는 적당한 묶음)으로 기록하고, 개체마다 다시 접기는 한 번만 한다. 사실 하나씩 API 를 부르는 방식보다 쿼리가 훨씬 적다.
- 업체가 보낸 원본은 그대로 남긴다(로드맵의 원본 보관). 정규화가 틀렸을 때 다시 해석할 수 있어야 한다.
- 모의 업체로 바꿔 끼우는 지점은 `docs/testing.md` 에 예약한 `APP_MODE=test` 다. 어댑터의 업체 호출 부분만 모의 구현으로 바뀐다.
- 기존 `POST /unit-events` 는 그대로 둔다. 수기 입력과 플레이북에 쓴다.

## 정책 변경 지점

누가 무엇을 보고하고 누가 판정하는지는 바뀔 수 있다(사용자 확인 2026-10-03). 그래서 **사실의 구조는 고정하고, 정책은 데이터로 둔다.**
모든 정책을 지금 구현하지 않는다. 정책이 바뀌면 행 하나를 고치거나 판정 함수 하나를 더하는 정도로 끝나게 세 지점을 열어 둔다.
규칙 엔진은 만들지 않는다.

### 1. 파트너 능력 프로필

거점(창고·서비스센터)과 외부 파트너 기준 정보에 "무엇을 보고해 주는가, 무엇을 정하는가"를 둔다.

| 항목                          | 뜻                                                                                    | 쓰이는 곳                                                                                                               |
| ----------------------------- | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `reports_serials_on_receipt`  | 입고 때 시리얼 목록을 준다                                                            | 통지된 시리얼이 입고되지 않았다는 이상은 이 값이 참일 때만 낸다                                                         |
| `reports_serials_on_shipment` | 출하(선적) 때 시리얼 목록을 준다                                                      | 선적 줄에 시리얼 목록을 기대할지                                                                                        |
| `reports_serials_on_outbound` | 출고 때 시리얼을 스캔해 준다                                                          | 주문 출고 항목에 시리얼이 붙는 유일한 경로. 거짓이면 어느 개체가 어느 주문으로 나갔는지 알 수 없다 (아래 "출고 시리얼") |
| `unit_receipt_trigger`        | 시리얼을 주지 않을 때 개체를 "창고에 들어옴"으로 볼 단계: `GOODS_RECEIPT` / `PUTAWAY` | 입고 추론을 어느 사실에서 할지                                                                                          |
| `reports_inspection_result`   | 검수 결과를 값(양품·불량·보류)으로 준다                                               | 거짓이면 처분을 재고 존 이동·폐기 수량에서 추론하고 "추론" 표시                                                         |
| `decides_disposition`         | 처분을 이 파트너가 정한다                                                             | 처분 판정 사실의 `decided_by` 기대값                                                                                    |
| `requires_hub_confirmation`   | 파트너 판정을 우리가 확정해야 실행으로 본다                                           | 참이면 판정과 실행 사이에 확정 단계가 생긴다                                                                            |

정책이 바뀌면 이 행을 고친다. 판정 함수는 이 값을 인자로 받는 순수 함수라 함께 테스트된다.

### 2. 시리얼은 제품이 아니라 사실 단위로 붙는다

- 제품의 `tracking_mode = SERIAL` 은 "이 제품은 개체마다 시리얼이 있다"는 뜻일 뿐, 모든 단계가 시리얼을 보고한다는 뜻이 아니다.
- 입고 줄은 언제나 **수량**으로 기록하고, 파트너가 시리얼을 주면 그 사실에만 시리얼 목록을 붙인다.
- **샘플링 검사에서 나온 불량 시리얼**은 수량 입고 줄에 매달린 시리얼 단위 검수 사실(`INSPECTION`, 결과 불량)로 기록한다. 그 개체들만 이력이 시작된다.
- 개체의 이력은 처음 시리얼이 보고된 지점에서 시작한다: 제조사 출하 목록, 입고 스캔, 샘플 검사, 출고 스캔 중 어디든.

**현재 사정 (사용자 확인 2026-10-03)**

- **제조사는 출하 때 반드시 시리얼을 스캔한다.** 선적 줄의 시리얼 목록은 항상 온다. 개체가 어느 발주·어느 선적으로 들어왔는지는 이것으로 언제나 안다.
- 3PL 은 지금 입고 때 스캔하지만 하지 않게 될 수 있다. 3PL 에게 입고는 "입고 주문의 수량이 맞는가"의 문제이기 때문이다.
- 샘플링 불량 검사는 **3PL 의 입고 검사**다. 불량 기기의 시리얼은 그때 온다.

**3PL 이 시리얼을 주지 않을 때 개체의 입고를 어떻게 기록하나**

입고 주문(창고에 보내는 입고 예정)에 선적의 시리얼 목록이 실려 가고, 창고가 그 주문을 **적치 완료**하면 목록의 개체가 창고에 들어온 것으로 본다(현재 운영, 사용자 확인 2026-10-03). 즉 선적 줄의 시리얼 목록과 적치(또는 입고 확정) 수량으로 추론한다. 어느 단계에서 추론할지는 `unit_receipt_trigger` 로 바꾼다. 추론한 사실은 "추론"으로 표시하고, 모르는 것은 단정하지 않는다.

| 적치(또는 입고 확정) 수량 | 개체 이력에 남기는 것                                                                                                                                                                  |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 선적 줄 수량과 같다       | 그 줄의 시리얼 전부에 `RECEIVED`·`STORED`(추론)                                                                                                                                        |
| 적다 (부족)               | 어느 시리얼이 빠졌는지 모르므로 개체 단위로는 추론하지 않는다. 선적 줄에 부족 이상을 내고, 개체들은 "입고 미확인"으로 둔다. 출고 스캔·샘플 검사 등으로 시리얼이 나타나면 그때 확정된다 |
| 많다 (초과)               | 통지 목록 전부에 `RECEIVED`(추론) + 초과 이상. 목록에 없는 개체는 나중에 시리얼이 보고될 때 이력이 시작된다                                                                            |

3PL 이 시리얼을 주면(`reports_serials_on_receipt` 참) 추론하지 않고 직접 보고된 시리얼로 기록하고, 통지 목록과 대조해 이상을 낸다.
샘플 검사의 불량 시리얼은 어느 경우든 직접 보고된 사실이다.

**출고 시리얼**

3PL 은 지금 출고 때 시리얼을 스캔한다. 이 스캔은 입고 스캔과 무게가 다르다.

- 입고 시리얼은 제조사 목록으로 대신할 수 있지만, **출고 시리얼은 대신할 곳이 없다.** 같은 SKU 여러 개 중 어느 개체가 어느 주문(어느 패키지)으로 나갔는지는 출고 스캔에서만 알 수 있고, 이 시스템의 목표("어떤 주문의 어떤 패키지로 어떤 SN 이 나갔나")가 여기에 달려 있다.
- 업계에서 출고 스캔이 언제나 필수인 것은 아니다. Dynamics 365 는 시리얼을 판매(포장·송장) 시점에만 등록하는 모드를, Oracle 은 출고 피킹 때만 받는 모드를 공식 옵션으로 둔다. 국내 풀필먼트 공개 문서에는 시리얼 기능 자체가 없다 ([research/korean-3pl-wms-inbound.md](research/korean-3pl-wms-inbound.md)). 즉 출고 스캔은 3PL 의 기본 기능이 아니라 계약으로 요구하는 서비스다.
- 이 스캔에 기대는 것들: 보증·AS 는 시리얼로 조회한다(Apple·Samsung 보증 정책). 리콜 공표는 일련번호 또는 로트로 범위를 특정한다(제품안전기본법). 이 시스템의 DOA 처리도 시리얼로 주문 항목을 찾는다.
- 그래서 `tracking_mode = SERIAL` 제품의 출고에 시리얼이 없으면 이상으로 표시한다. 3PL 이 출고 스캔을 멈추면 주문↔개체 연결이 끊기므로, 이는 프로필 값으로 흡수할 정책 변경이 아니라 **3PL 계약에서 지켜야 할 요건**으로 본다.

### 3. 처분 판정은 판정자를 담은 사실이다

- 처분 판정 사실에 `decided_by`(역할: `WAREHOUSE`, `SERVICE_VENDOR`, `HUB_OPERATOR` …)와 `confirmed_by`(없을 수 있음)를 둔다.
- **지금(E 의 답)**: 경로 A 는 창고가, 경로 B 의 폐기는 AS 센터 수리기사가 정한다. 우리는 받은 판정을 기록한다(선택지 1).
- **DOA 의 고객 보상**: AS 센터 수리기사가 DOA 로 판정해 폐기를 정하면 고객에게는 새 제품이 출고된다(사용자 확인 2026-10-03). 즉 교체/환불 결정은 선택지 A(AS 확정 시점)이고 결과는 교체다. 지금 구현(`as.doa.confirmed` → OMS 교체 출고 항목)이 이와 같다. 보상 방식은 열거값(`REPLACE`, 나중을 위해 `REFUND` 예약)으로 두되, 환불 경로는 아직 만들지 않는다.
- 파트너의 `requires_hub_confirmation` 을 켜면 같은 사실 구조 위에 우리 확정 단계가 더해진다(선택지 3). 스키마는 바뀌지 않는다.
- 판정자가 바뀌어도(예: 제조사가 반송 여부를 정하게 됨) 역할 값 하나가 늘 뿐이다.

## 결정 전에 확인이 필요한 것

아래는 조사로 메울 수 없었다. 일반 관행이 아니라 **우리 거래처와 계약의 실제 사정**을 알아야 정할 수 있다.

## 구현 순서

서비스 구조 개편은 끝났다([architecture-rules.md](architecture-rules.md)). 각 단계가 PR 하나다.

1. `catalog` 에 추적 방식, `unit` 에 제품 등록(명령, `REGISTERED` 사실, `registeredAt`, 미등록 출고 이상), 재고 조회의 등록/미등록 구분, 기기 변경 피드와 결과 API, 모의 기기 서버 `apps/device-api`, 등록 플레이북. 선적이 아직 없으므로 이 단계의 등록 명령은 시리얼 목록을 받는다. 선적 단위 등록은 5단계에서 더한다
2. 거점·파트너 능력 프로필 (정책 값)
3. `warehouse` 수량 원장과 재고 조회 통합
4. `procurement` 발주 등록·변경·종결
5. `transport` 선적(시리얼 목록), 운송 서류, 컨테이너, 운송 사실과 정정
6. `warehouse` 단계별 입고 보고, 적치 시 개체 입고 추론, 제품 이력·수량 원장 반영, 정정 전파, 배치 어댑터 뼈대(체크포인트, 대량 기록 usecase, 모의 업체)
7. 발주 줄 단계별 수량과 이상 조회, 운송 중 재고
8. 역흐름: 반품 케이스, 처분 판정 사실(`decided_by`), 경로 A·C 의 사실
9. 웹 콘솔 화면, 플레이북 확장

1·2 는 독립적이고, 3 → 4 → 5 → 6 은 순서대로, 7 은 6 뒤, 8 은 6 뒤, 9 는 각 단계에서 조금씩.

## 근거의 수준

이 설계안의 내용을 근거에 따라 나누면 이렇다.

**원출처로 확인한 것**

- 인도 조건(Incoterms)은 위험 이전만 정하고 소유권 이전은 정하지 않는다 (ICC Incoterms 2020 서문).
- SAP 는 "도착했지만 미수락"과 "수락"을 다른 이동 유형으로 전기하고, 정정은 역분개 문서로 한다 (SAP Learning, 테이블 정의).
- SAP 인바운드 딜리버리는 줄 단위로 발주 줄을 참조한다 (LIPS 테이블 정의). X12 856 은 선적 아래 주문 루프를 여러 개 둔다.
- 해운 표준(DCSA Track & Trace 2.1)은 사실을 계획·예상·실적으로 구분하고 발생 시각과 기록 시각을 따로 둔다.
- 컨테이너 번호는 ISO 6346 형식이고 체크디지트가 있다.
- SAP 와 Odoo 는 추적 방식을 제품 단위로 정한다.

**2차 자료나 검색 요약에만 근거한 것**

- B/L 과 컨테이너의 다대다 관계, Master/House 구분.
- EDI 입고 통지(X12 861, EDIFACT RECADV)의 수량·사유 코드 세부.
- 수입신고번호·화물관리번호의 자릿수 구성.

**사용자에게 확인한 것 (2026-10-03)**

- 제조사는 출하 때 반드시 시리얼을 스캔한다. 3PL 입고 스캔은 지금 되지만 바뀔 수 있다. 샘플 불량 시리얼은 3PL 입고 검사에서 온다.
- 처분 판정은 창고(경로 A), AS 센터 수리업자(경로 B 폐기)가 한다.
- 정책은 바뀔 수 있으니 적은 수정으로 반영할 구조를 원한다.

**근거 없이 고른 것 (위 확인이 필요한 이유)**

- 역흐름에서 반품 케이스·처분 판정을 둘 도메인 (E 의 답에 따라 정한다).

- 입고 단계 네 개와 `GOODS_RECEIPT` 만 필수라는 구성. 국내 WMS 는 한 곳만 확인했다.
- 운송 진행 코드 9개. 해상·항공·육상 표준에서 추려 직접 만든 집합이고, 어느 업체가 무엇을 주는지 모른다.
- 발주 필드의 필수·선택 구분.
- 국내 육상 운송의 식별자.

## 조사에서 확인하지 못한 것

설계에 영향이 있는 것만 적는다.

- 국내 3PL WMS 들이 입하·검수·입고·적치를 각각 보고하는지. 한 곳만 확인했고 그곳은 입고 한 번만 보고한다. 설계는 단계 생략을 허용하므로 어느 쪽이든 담을 수 있다.
- 국내 육상 운송의 표준 식별자. 운송장 번호 + 운송사로 가정했다.
- 수입신고번호·화물관리번호의 자릿수 구성은 관세청 원문과 대조하지 않았다. 형식 검증은 넣지 않는다.
- 회계 기준상 재고 인식 시점. 소유권 이전 지점을 사용자가 정하게 한 이유다.
