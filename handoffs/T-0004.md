## 한 일

- 선적 무효화가 내는 시리얼별 `scm.unit.event-voided` 대량 발행을 아웃박스 relay, Redis Streams 구현, OMS 소비자 코드로 따라가 봤다. 결론: **새로운 규모 문제가 아니다.** 같은 선적을 받을 때 입고 경로(`recordAll`)가 이미 시리얼마다 `event-recorded` 를 한 건씩 낸다. 무효화는 그 거울상이라 비용이 같다. OMS 는 DISPATCHED 사실에 쿼리를 하나도 하지 않는다.
- 선택지 셋((a) 시리얼별 유지, (b) 선적 단위 이벤트, (c) 그 밖)의 바뀌는 파일, 규격 호환성, 순서 보장을 정리했다. PR 1 은 **(a) + 일괄 정정 메서드**로 가고 규격은 바꾸지 않을 것을 권고한다. 결정은 사람이 한다.
- 기기 요청 질문의 답: DISPATCHED 를 무효화해도 `registeredAt` 은 바뀌지 않는다. DEACTIVATE 는 드문 경우에만 나오고 REGISTER 는 나오지 않는다(근거는 3절).

**5,000건일 때 예상 동작 (계산이며 측정은 하지 않았다)**

- 발행: flush 100번, 순차 `XADD` 5,000번, UPDATE 100번. 지연은 Redis 왕복 5,000번과 트랜잭션 100번이 좌우한다. 걸리는 시간은 재지 않았다.
- 소비: `XACK` 5,000번 + 루프 약 500바퀴(`XAUTOCLAIM`·`XREADGROUP` 약 1,000번). OMS DB 에는 부하가 없다.
- 같은 트랜잭션에서 기기 요청 알림이 생기면 void 5,000건 뒤에 나간다. 그만큼 기기 서버 알림이 늦어진다.
- 50,000건이면 위 숫자가 모두 10배다.
- 실패: 업무 트랜잭션은 한 번에 커밋되거나 롤백된다. relay 가 중간에 실패해도 표시한 곳까지만 나가고 다음 tick 에서 이어간다(at-least-once). OMS 쪽은 DISPATCHED 를 처리하다 실패할 곳이 사실상 parse 뿐이다. parse 에 실패하면 ack 하므로 막히지 않는다.

### 3. PR 1 범위 권고 (결정은 사람)

**넣을 것**

- (a) 그대로 간다. 규격 변경 없이 일괄 정정 메서드를 둔다(예: `UnitService.voidAll(targets, { reason, actor })`). `recordAll`·`registerAll` 과 같은 모양으로 만든다.
- 설계 요점:
  1. **잠금 순서를 입고와 맞춘다.** 입고는 트랜잭션의 첫 쿼리로 발주 행을 잠그고, 그다음에 `shippedQuantities` 를 읽는다(`intake-shipments.usecase.ts` 72–73, 130–136). 무효화는 `shippedQuantities` 를 바꾼다. 발주 행을 먼저 잠그지 않으면 동시에 들어온 입고가 옛 누계로 `OVER_SHIPPED` 를 계산한다. 연결된 선적: 발주 행 → 선적 행(`findByShipmentNoForUpdate`, `apps/scm-api/src/domains/transport/application/shipment.service.ts` 108) → 개체 순서로 잠근다. 미연결 선적은 발주가 없으니 선적 행부터 잠근다.
  2. 개체는 `lockBySerials` 로 잠근다. 잠그는 순서는 시리얼 순으로 고정되어 있다(`unit.repository.ts` 8). 사실 조회는 잠근 `unitId` 목록 + `type = 'DISPATCHED'` + `source_ref IN (선적 번호, 연결 전 번호)` 로 한다. `unit_events` 인덱스는 `(unit_id, occurred_at)` 하나뿐이다(`apps/scm-api/src/db/schema.ts` 144). 그래서 `source_ref` 만으로 찾지 않는다.
  3. **이미 정정된 사실은 건너뛴다.** 단건 경로는 `UNIT_EVENT_ALREADY_CORRECTED` 를 던진다(`unit.service.ts` 231–233). 일괄 경로에서는 `unit_event_corrections` 에 행이 없는 것만 고른다(`target_event_id` unique, `schema.ts` 153–156). 건너뛴 건수를 결과로 돌려준다. 저장소에는 `addCorrections`(일괄)를 더한다.
  4. 정정 INSERT를 한 번에 하고, 사실마다 `event-voided` 를 적고, `listEffectiveEventsOf` 를 한 번 부르고, 개체마다 `projectUnit` → `updateState` → `activationChange(before, after)` 를 한다. `before` 는 갱신 전에 따로 떠 둔다(`recordAll` 146–151 과 같은 이유).
  5. 대체 사실은 없다(재제출은 입고 경로로 들어온다). 그래서 `event-voided` 의 `replacementEventId` 는 null 이다.
- **기기 요청(DEACTIVATE)**
  - 무효화는 `registeredAt` 을 건드리지 않는다. `REGISTERED` 는 상태 전이와 따로 접힌다(`apps/scm-api/src/domains/unit/domain/unit-projection.ts` 91–93). 등록된 개체는 무효화 뒤에도 등록된 상태다.
  - `shouldBeActive` 는 `registeredAt !== null && status ∉ {DOA, SCRAPPED}` 다(`unit-activation.ts` 10–11). 그래서 요청이 나오는 경우는 다시 접은 결과가 DOA·SCRAPPED 로 바뀔 때뿐이다. 코드를 읽고 따져 본 결과이며 테스트로 확인하지는 않았다.
    - DISPATCHED 가 마지막 물리 사실이었고 그 앞 사실의 결과가 SCRAPPED·DOA 였다 → DEACTIVATE. 입고 주석의 "폐기된 등록 개체가 다시 출발 보고됨"(`intake-shipments.usecase.ts` 301)을 거꾸로 한 경우다.
    - DOA → DISPATCHED → RETURN_RECEIVED → 무효화 뒤에는 RETURN_RECEIVED 가 DOA 를 이어받는다(`unit-projection.ts` 123). → DEACTIVATE.
    - 흔한 경우(DISPATCHED 가 첫 사실): 상태가 UNKNOWN 으로 돌아가고, 등록 여부와 상관없이 활성 여부가 같다 → 요청 없음.
    - DISPATCHED 는 DOA 를 만들지 않으므로 REGISTER 는 나오지 않는다.
    - 뒤에 RECEIVED 같은 사실이 있으면 다시 접을 때 `anomalies` 가 생긴다. 입고 뒤 무효화를 허용할지(D5, 06 "선적의 정정")와 이어지는 문제다.
  - **기기 요청은 무효화 한 번에 하나로 묶는다**(항목 = DEACTIVATE 가 나온 개체들). 등록 명령이 배치를 요청 하나로 만드는 방식과 같다(`unit.service.ts` 195). 반면 입고는 개체마다 요청을 하나씩 만든다(`intake-shipments.usecase.ts` 351–360). 두 방식이 다르다는 점을 적어 둔다.
  - `reason` 은 `correctionDeviceRequestReason('DEACTIVATE', 'DISPATCHED', undefined)` 를 쓰면 `'DISPATCHED'` 가 된다(`unit-activation.ts` 40). 운영자가 보면 "출발 때문에 비활성화"로 읽혀 오해를 부른다. `reason` 은 자유 문자열이다(`packages/contracts/src/scm.ts` 397). usecase 에서 `'SHIPMENT_VOIDED'` 를 넘기기를 권고한다. 순수 함수는 고치지 않아도 된다.
- 검증(PR 의 `검증` 칸): 5,000 시리얼 선적을 입고 → 무효화하고 다음을 실제로 잰다. `outbox_events` 미발행 수가 0이 되는 데 걸리는 시간, `XINFO GROUPS scm.unit-events` 의 `oms-api` `lag`·`pending` 이 0이 되는 데 걸리는 시간(`docs/playbooks/cross-service.md` 67–72), 무효화 요청의 응답 시간. 같은 조건으로 입고 시간도 재서 나란히 적는다.

**뺄 것**

- (b) 선적 단위 이벤트: 규격 변경, 순서 보장 상실, 메시지 크기 문제가 있다. 지금 이 이벤트를 원하는 소비자도 없다.
- (c1) `EventOutbox.enqueueAll`: 공용 패키지(db-kit·nest-kit)를 고친다. 입고도 덕을 본다. PR 1 측정에서 무효화나 입고 트랜잭션이 무겁게 나오면 별도 PR 로 한다.
- (c2) 비동기 청크: 원자성을 잃는다. 실제 선적 크기를 알기 전에는 넣지 않는다(사람에게 묻기 1).
- relay 의 `XADD` 파이프라이닝, 스트림 트림(MAXLEN), DLQ: 운영 과제다(`docs/05-roadmap.md` "운영"). PR 1 과 상관없다.

## 사람에게 묻기

1. **실제 선적 한 건의 시리얼 수(보통·최대).**
   - 왜 필요한가: 규격 상한은 50,000 이다(`packages/contracts/src/transport.ts` 29). 이 크기를 한 트랜잭션으로 무효화해도 되는지에 따라 (a)만으로 충분한지, (c2) 청크 처리가 필요한지가 갈린다. 입고도 같은 크기를 한 트랜잭션으로 받으니, 답은 입고 설계에도 적용된다.
   - 누구에게: 구매·물류 담당자에게 B/L 하나에 실리는 시리얼 수를 묻는다. 업체 출하 목록 표본이 있으면 그것이 더 정확하다.
   - 결과: 수천 건 수준이면 (a)로 충분하다(권고). 수만 건이 흔하면 PR 1 측정 결과를 보고 (c1) 다음 (c2) 순서로 검토한다.
2. **(a)와 (b) 중 무엇으로 갈지.** 권고는 (a)다. (b)는 규격 변경(`!`·`BREAKING:`), 순서 보장 상실, 메시지 크기 문제가 있는데 얻는 것은 메시지 수 하나뿐이다. 입고 뒤 무효화(D5)는 이미 열려 있으니 여기서 다시 묻지 않는다.
