무효화가 바꾸는 것 (구현자가 놓치기 쉬운 것)

1. `shippedQuantities` 는 무효 선적의 줄을 뺀다. 발주 줄 `shippedQty` 가 줄어든다.
2. `countByPurchaseOrders` 는 무효 선적도 센다. 차수 번호를 다시 쓰지 않는다(`shipment_no` unique). 대체 제출은 다음 차수를 받는다.

4. 이 선적이 만든 `DISPATCHED` 사실을 모두 정정(무효화)한다. 찾는 조건: 종류 `DISPATCHED`, 출처 참조가 선적 번호 또는 연결 전 번호(`shipment_links.previous_shipment_no`), 시리얼이 이 선적의 목록에 있음(C7). 개체마다 다시 접고, 활성 여부가 바뀌면 기기 요청을 만든다.
5. 지금 `UnitService.correct` 는 사실 하나씩이고 시리얼마다 `scm.unit.event-voided` 를 아웃박스에 적는다. 시리얼 5,000 개 선적이면 메시지 5,000 개다. 일괄 정정 경로(잠금·삽입·다시 접기를 묶음으로)가 필요하고, OMS 소비자가 이 양을 받을 수 있는지 확인해야 한다.

**C4. 코드 체계**

- a: 06 의 9개를 그대로 두고 업체 코드는 `vendor_code` 에 남긴다. 업체 코드 → 우리 코드 매핑은 어댑터(6단계)가 한다. DCSA 는 `GTIN`/`GTOT` 의 선적항·양하항 구분을 장소로 하므로 매핑에 서류의 선적항·양하항이 필요하다.
- b: DCSA 처럼 (종류, 표준 코드, 장소)로 저장하고 9개는 조회용 분류로 계산한다. 표준이 바뀌어도 저장 구조가 그대로지만, 항공·국내는 DCSA 코드가 없어 다시 매핑이 필요하다.
- `DELIVERED_TO_WAREHOUSE`: 운송사의 배송 완료 증빙(POD)이면 `transport` 에 남기고, 창고가 보고하면 6단계 `warehouse` 의 `ARRIVAL` 로 본다. 누가 보고하는지(확인 항목 1·7)를 모르면 코드는 남겨 두고 쓰지 않는다.

**C5. 선적 정정의 단위**

- a: 선적 전체 무효화 + (필요하면) 대체 제출. 줄 수량이나 시리얼 목록이 틀려도 같은 경로. 구현이 작고, "보고 한 건"이 단위인 5a 와 맞는다. 대체 제출은 새 차수 번호를 받는다.
- b: 줄 단위 정정(줄 하나의 수량·시리얼 무효화·대체). 차수 번호가 유지되지만, 줄의 발주 맞춤·누계·`DISPATCHED` 연쇄를 줄마다 다시 해야 한다.

**C6. 업체가 보낸 수정본을 어떻게 받나** (06 "업체 연동 방식"의 멱등 키와 부딪힌다)

- 06 은 "멱등 키는 업체 쪽 레코드 id"라고 했다. 업체가 같은 레코드를 고쳐서 다시 내보내면(같은 id, 다른 내용) 이 키로는 **수정본이 중복으로 버려진다.**
- a: 멱등 키 = 레코드 id + 업체 쪽 버전(수정 시각 등). 같은 id 의 새 버전은 자동으로 앞 보고를 무효화하고 대체한다.
- b: 멱등 키 = 레코드 id + 내용 해시. 같은 id 인데 내용이 다르면 기록하고 이상(`RESUBMITTED_WITH_CHANGES`)으로 표시해 운영자가 무효화를 결정한다.
- c: 수정본은 업체가 새 레코드로 낸다고 보고 지금 방식을 유지한다.
- 어느 것이 맞는지는 업체가 수정을 어떻게 내보내는지에 달렸다(묻기 B5). 5a 의 제출도 같은 문제를 가진다.

**C7. 선적과 `DISPATCHED` 사실을 무엇으로 잇나**

- a: 지금처럼 출처 참조(선적 번호, 연결 전 번호)와 시리얼로 찾는다. 스키마를 바꾸지 않고 5a 에 이미 기록된 사실에도 쓸 수 있다. 문자열 참조라 번호 규칙이 바뀌면 깨진다.
- b: `unit_events` 에 선적 줄 참조 칼럼(nullable)을 더한다. 06 이 6단계 `RECEIVED` 에 "발주 줄·선적 줄 참조를 붙인다"고 했으므로 같은 칼럼을 쓰게 된다. 5a 의 기존 사실은 채워 넣는 이행(또는 a 로 대체)이 필요하다.
- c: `DISPATCHED` 의 `idempotency_key` 를 `선적 id + 시리얼` 로 정해 둔다. 칼럼을 늘리지 않지만 키 문자열에 뜻을 싣는 방식이다.

**C8. 순서 이상을 언제 계산하나**

- a: 읽을 때 유효한 `ACTUAL` 들로 계산한다(`projectUnit` 이 개체 이상을 다시 접을 때 계산하는 것과 같은 방식). 배치가 순서 없이 가져와도(출발 보고가 도착 보고보다 늦게 와도) 결과가 같고, 정정이 들어오면 바로 반영된다.
- b: 받을 때 고정한다(선적 이상과 같은 방식). 늦게 온 사실 때문에 이미 붙은 이상이 남아, 배치 순서에 따라 결과가 달라진다.
- 선적 이상을 고정한 이유("도착 당시 넘쳤는가")는 운송 사실의 순서에는 해당하지 않는다고 본다(분석).

## 다음 제안

1. 소유자가 D1–D9 를 정하면 위 5 의 PR 1(선적의 정정)부터 `developer` 작업 단위로 넘긴다. PR 1 은 D3(C5·C7)·D5 만 정해지면 거래처 답 없이 진행할 수 있다.
2. PR 2·3 의 작업 지시에 넣을 것: ISO 6346 시험 값(`NARU3472484`, `KKFU6671914`, `APZU4812090`, `CSQU3054383`, 나머지 10 경우), 무효 선적을 빼야 하는 세 쿼리와 빼면 안 되는 차수 계산, 예상(`ESTIMATED`)은 정정하지 않고 최신 기록이 이긴다는 규칙, `vendor_code` 보관.
3. 사용자에게 B1–B7 조사를 요청한다. B2·B3·B5 는 같은 포워더 담당자에게 한 번에 물을 수 있다. B6 은 `customs-trade-expert`, B7 은 `reverse-logistics-expert` 와 같이 올린다.
4. 일괄 정정으로 `scm.unit.event-voided` 가 수천 건 나갈 때 OMS 소비자가 감당하는지 `architect` 가 PR 1 전에 본다.
5. 승인되면 3 의 "06 에 반영할 초안"을 director 가 06 에 옮긴다.
